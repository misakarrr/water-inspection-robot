# 水利巡检机器人导航原型设计

## 1. 目标

在 Ubuntu 22.04、ROS 2 Humble、Isaac Sim 4.x 和 Nav2 上完成一个零基础可逐步验收的自主巡检导航原型。第一阶段将四足机器狗作为简化移动底盘处理，不模拟四足步态；先验证固定地图上的巡检点导航，再逐步加入激光雷达定位和在线建图。

硬件基线为 RTX 3090（24 GB 显存）。该显卡用于本地仿真和可视化；首版使用中等规模场景和传感器配置，避免在模型和渲染质量尚未成为目标时消耗显存。

## 2. 采用路线与取舍

本设计采用“资产优先跑通导航原型，再替换实验室机器人模型”的路线。先用简化底盘或 Isaac Sim 官方机器人资产验证完整链路，之后盘点实验室已有的 URDF、USD、网格和控制代码并逐项接入。这样机器人资产不完整时，导航工作仍可开展。

不采用真实机器人模型优先的路线，因为目前模型与控制接口尚未盘点；也不先用另一套仿真器验证后再迁移，因为场景和传感器接口会重复适配。

## 3. 版本与运行基线

- 操作系统：Ubuntu 22.04 原生安装。
- ROS：ROS 2 Humble，包括 Nav2、RViz2、地图服务和后续 AMCL / SLAM Toolbox。
- 仿真：Isaac Sim 4.x；安装前按 NVIDIA 对应版本的官方系统要求和 ROS 2 Bridge 兼容表，固定一个具体补丁版本并记录 NVIDIA 驱动版本。
- GPU：RTX 3090，按 24 GB 显存配置中等场景；首轮不运行大规模 Replicator 数据生成或强化学习训练。
- ROS 2 与 Isaac Sim 初期在同一台 Ubuntu 机器运行，统一启用仿真时钟。

Isaac Sim 4.x 的具体补丁版本必须由安装时官方兼容矩阵确定；不得只因“4.x”相同就混用不同版本的扩展示例或 API。

## 4. 场景范围

首个场景由简单几何体和按需选用的官方资产组成，包含：

- 一条带 90 度转弯的巡检道路。
- 一面可供后续拍摄的混凝土墙。
- 数个固定障碍物。
- 一个可视化标记的禁入区域。
- 起点和 3 至 5 个巡检点。

场景首先采用米制、Z 轴向上，并具有可供机器人和障碍物使用的碰撞体。首阶段的固定地图表示已知静态结构；若场景调整，必须同步重新导出或更新地图和禁入区 mask。

## 5. 组件边界与数据流

```text
Isaac Sim 场景与简化移动底盘
  ├─ /clock
  ├─ 仿真位姿 / 里程计 → /odom、odom → base_link
  ├─ 后续加入的激光雷达 → /scan
  └─ /cmd_vel ← ROS 2 底盘适配层
                         ↑
              Nav2 Planner / Controller
                         ↑
              Waypoint Follower 巡检点序列
```

ROS 2 包按职责拆分：

- `inspection_robot`：底盘运动适配、机器人状态和传感器接口。
- `inspection_bringup`：Nav2 参数、地图、禁入区 mask、启动文件和 RViz 配置。
- `inspection_mission`：巡检点列表与顺序执行；第一版仅负责到点和结果记录，不处理病害识别。

首版将底盘按差速移动模型简化：适配 `/cmd_vel` 中的 `linear.x` 和 `angular.z`；暂不使用 `linear.y`。Nav2 的具体控制器和机器人 footprint 参数必须按简化模型及场景通道宽度配置。

## 6. 分阶段定位设计

### 阶段 A：仿真真值定位

使用已知静态地图。仿真真值位姿作为里程计来源，发布 `/odom` 和 `odom -> base_link`；初始地图与仿真世界对齐时，将 `map -> odom` 设为恒等变换。该模式用于隔离定位误差，先验证 Nav2 规划、速度控制和巡检点执行。

阶段 A 的验收范围限于已知地图上的静态障碍和禁入区路线规划，不声称具备真实传感器避障能力。

### 阶段 B：激光雷达与 AMCL

增加模拟激光雷达并发布 `/scan`。运动里程计继续发布 `/odom` 与 `odom -> base_link`；AMCL 根据 `/scan` 和静态地图发布 `map -> odom`。同一条巡检路线用于比较真值定位和 AMCL 模式下的导航结果。

### 阶段 C：SLAM 评估

只有在需要验证未知环境建图时才增加 SLAM Toolbox。建图、保存地图、重启后在保存地图上定位导航作为独立验收；SLAM 不作为首个导航闭环的前置条件。

## 7. Nav2 与巡检任务

Nav2 负责全局路径规划、局部控制和目标点执行。固定地图以 ROS 2 map server 可读的 OccupancyGrid 文件为准；初期可从场景俯视结果制作并校验，不把任何特定 Isaac Sim 扩展作为唯一地图来源。

禁入区使用 Nav2 KeepoutFilter 的 mask 表示，并在 Isaac Sim 场景中以明显颜色标记。巡检任务在下发路线前检查巡检点不位于禁入区内。第一版要求机器人不会规划或驶入 mask 标记区域。

巡检点使用 Waypoint Follower 顺序执行。到达点后确认导航动作成功并记录点 ID、仿真时间和位姿，然后继续下一个点。相机拍摄和病害识别在本项目的后续阶段接入。

## 8. 话题与坐标系约定

| 名称 | 类型 | 首版用途 |
|---|---|---|
| `/clock` | `rosgraph_msgs/msg/Clock` | Isaac Sim 仿真时钟；相关 ROS 节点统一使用 `use_sim_time` |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | Nav2 到简化底盘的速度指令 |
| `/odom` | `nav_msgs/msg/Odometry` | 阶段 A 使用真值；阶段 B 切为运动里程计来源 |
| `/tf` | `tf2_msgs/msg/TFMessage` | 发布 `map -> odom -> base_link` 动态变换 |
| `/tf_static` | `tf2_msgs/msg/TFMessage` | 发布固定传感器安装变换 |
| `/scan` | `sensor_msgs/msg/LaserScan` | 阶段 B 起供 AMCL 与局部代价地图使用 |

固定传感器坐标系通过 `base_link -> sensor_link` 连接。任何模式下都必须保证 TF 树无断链，且同一动态 TF 不可由两个节点同时发布。

## 9. 验收目标

1. 环境：Isaac Sim 和 ROS 2 Humble 分别通过最小启动检查，ROS 2 Bridge 可交换 `/clock`。
2. 场景：道路、墙、转弯、障碍物、禁入区可重复加载，米制和碰撞设置正确。
3. 控制：ROS 2 发布 `/cmd_vel` 时机器人在仿真中移动；停止命令后停止；`/odom` 和 TF 连续有效。
4. 真值导航：Nav2 可到达全部巡检点，不能通过禁入区；整条路线连续运行 10 次，无碰撞且每个导航动作都有明确成功或失败状态。
5. AMCL：加入 `/scan` 后，可在设置初始位姿后完成同一条路线；RViz 中地图、激光点云和机器人位姿对齐。
6. SLAM：若进入阶段 C，能生成并保存地图，重新启动后在该地图上完成路线。

## 10. 非目标与风险

本导航原型不包含裂缝或渗水识别、合成数据训练、四足步态强化学习、坡面攀爬、真机安全认证和真实设施部署。四足真机后续是否能复用差速接口，取决于其控制器是否能可靠跟踪平面速度命令；如果不支持，需要在底盘适配层替换为实验室步态控制接口，但 Nav2 的上层话题和任务流程尽量保持一致。

主要风险是 Isaac Sim、ROS 2 Bridge 与 Humble 的补丁版本兼容、仿真时钟/TF 配置、真值与 AMCL 模式混用，以及地图 mask 的分辨率和原点与地图不一致。版本锁定、单一 TF 发布责任和地图叠加检查作为阶段验收的一部分。
